# BA — данные, ингест, критерии оценки, бизнес-кейс, сдача
Твои папки: `ingest/`, `validator/fidelity.py` (код пишет Claude Code под твоим ревью совместно с ML1), `data/`, `docs/` (кроме PROMPTS.md и ENGINE_NOTES.md), `README.md`.
Ты закрываешь **два критерия из трёх**: «репрезентативность материалов» и «бизнес-ориентированность» (20 баллов из 30). Это не вспомогательная роль.

## Задачи
**BA-1. Золотой набор входов (data/samples/).** 6–8 текстов в `.md`/`.txt`, реально похожих на энергетику: итоги года с финтаблицей (выручка/EBITDA, план-факт), отчёт по ремонтной кампании, инвестпрограмма, технический доклад с параметрами оборудования, протокол совещания с поручениями и сроками, презентация о компании (пример с титулом «Докладчик/дата»), короткая сводка для руководства. Минимум 3 с таблицами (md-таблицы или CSV-блоки) и 2 с числами только в прозе. Разные длины (0,5 – 4 страницы). Данные можно синтезировать, но без реальных конфиденциальных сведений; в README указать, что данные синтетические. Нумерация `01_… .md`.

**BA-2. Золотые планы (data/gold/).** Для 3 входов вручную написать эталон `DeckPlan` JSON (`NN_name.plan.json`) строго по `contracts.py`: структура слайдов, заголовки, буллеты, `table.source_id`, `evidence`. Это моки для ML2/ML1 и эталон для оценки. Первые 2 плана — **в первый же день**, остальные до M3.

**BA-3. Ingest (ingest/).** Реализовать `Ingestor` (код пишет Claude Code по твоему ТЗ ниже): разбор md-таблиц, CSV/TSV-блоков, таблиц, разделённых `|`; присвоение `table_id` (t1…), `source_hash` (sha256), нарезка на `SourceSection` по заголовкам/пустым строкам; ячейки — строки без нормализации. Ключевое требование: **ни одна цифра не меняется на этапе ингеста**. Тесты на всех образцах.

**BA-4. Fidelity-валидатор (validator/fidelity.py).** Реализация части `Validator`: (a) для каждого числового токена на итоговых слайдах (регулярка с учётом "19,1", "1 234,5", "≥ 10", процентов, годов) проверить, что он есть в `raw_text` источника → иначе `NUMBER_MISSING`; (b) таблицы: каждая ячейка PPTX == ячейка `SourceTable` (после разбиения на несколько слайдов — по объединению), иначе `TABLE_MISMATCH`; (c) каждая `Evidence.quote` — подстрока источника (нормализация пробелов) → иначе `EVIDENCE_NOT_FOUND`; (d) метрики `fidelity_numbers`, `fidelity_tables` в `ValidationReport.metrics`; (e) **обратная проверка полноты:** все числа источника, помеченные важными, не потеряны (warning).

**BA-5. Рубрика и оценка вручную.** `docs/EVAL_RUBRIC.md`: 4 оси × 0–2 (точность чисел, сохранение смысла, структура слайдов, соответствие шаблону) + флаг «открылось/правится в Р7». Оценить выходы по всем образцам, свести в `docs/EVAL_RESULTS.md`. Совместно с FS проверить в Р7 (`docs/R7_COMPAT_CHECKLIST.md`).

**BA-6. Бизнес-кейс и материалы сдачи.** (a) `docs/BUSINESS_CASE.md`: кто пользователь (специалист/референт, готовящий доклад), боль (перенос текста/таблиц, выравнивание, проверка оформления), процесс «как есть → как будет», **замер**: засечь время ручной сборки 2–3 образцов по шаблону ИнтерРАО vs время работы инструмента (честные цифры, допущения помечать), риски и границы применимости (приватность данных → замена модели на локальную/Yandex, ручная доводка). (b) `docs/CAPABILITIES_LIMITS.md`: что умеет (титул, разделы, текст, таблицы, разбиение больших таблиц, проверка чисел, смена модели) и чего нет (диаграммы, иконки, картинки, сложные объединённые таблицы). (c) `README.md` с запуском и примерами вход/выход (скрины). (d) сценарий демо на 5–7 минут: исходный текст → процесс генерации (лента стадий) → файл → открытие в Р7 → правка вручную → отчёт проверки. (e) питч: проблема → решение → архитектура одним слайдом → результаты на метриках.
